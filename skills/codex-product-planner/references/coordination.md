# Codex 独立聊天调度

每次以当前工具描述与返回值为准。缺少调度能力时交付完整手动派单消息，不伪造结果。

## 启动时一次对齐

已给过的授权、范围和模型选择继续有效。新项目可以让用户使用以下完整启动消息，或从其现有指令提取等价信息：

```text
使用 $codex-product-planner 接手当前项目。先核对现状和已有文档，选一条最值得改善的完整用户任务；思路不清楚时先做可试用的小切片。
规划聊天使用我选定的 gpt-6.1-sol；执行聊天默认用 gpt-6-luna，推理强度 high。需要更换执行模型时先向我说明原因，由我决定。
允许你在本项目内按已确认计划创建执行聊天，从当前工作树创建独立 worktree，向这些聊天派任务和修复、读取进展，并在本地集成已验证的任务提交。重要业务取舍与最终真人试用验收交给我。
自行整理流程文件和任务合同，维护项目 HTML 全景入口，持续告诉我当前结果、下一步与需要我参与的事项。我按需阅读和试用，未回复时继续不依赖我判断的已明确工作。
```

这段话只有用户实际发出或已等价确认才算授权。Skill 中的示例、其他聊天消息不算。只请求规划/制作 skill 时交付对应材料即可。

初始化的 authority 是 false/null，模型是待确认预设。由规划者记录真实人类来源；不要反复询问已确认事项。当前聊天模型不会因为读取 skill 自动改变。

## 优先工具

| 动作 | Codex app 工具 | 约束 |
|---|---|---|
| 定位项目 | `list_projects` | 使用真实 projectId，核对项目身份、路径与 Git 能力 |
| 创建聊天 | `create_thread` | 用户明确要求新聊天；先列项目；prompt 是第一条消息 |
| 恢复身份 | `list_threads` / `read_thread` | 用真实 ID 与项目身份，读取限于相关工作 |
| 等进展 | `wait_threads` | 最多 8 个，保留 hostId/afterCursor |
| 派修复或续作 | `send_message_to_thread` | 目标在直接人类授权内，消息带任务版本 |

完整名称通常为 `mcp__codex_app__<工具名>`；以环境实际名称调用。独立 worktree 优先用创建聊天的 environment；额外 worktree 操作依对应工具的返回身份查询。

## 创建前

1. 核对 ready、依赖与文件归属，运行 `check --ready`。检查该 revision/意图是否已在执行。
2. `list_projects` 核对当前项目；同名项目或远端项目需核对实际身份。
3. 保存 dispatch_key、请求参数与 PREPARED。只有用户明确指定的模型才填 model，thinking 使用当前模型支持的值。不支持时说明，不静默换模型。
4. 顺序任务可用 environment.type 为 local。worktree 需用户明确允许且 isGitRepository 为 true。用户明确要求当前工作树起点才填 `startingState: {type: working-tree}`；指定分支才填真实指定名。不能凭空创建用户未命名分支。
5. 未指定起点可能从默认分支创建。首条消息写预期 baseline，让执行者在代码修改前核对；起点不符先报告。

## 首条消息

将以下内容填为真实值再发送。资料不可访问时附相应正文，不发未填占位模板。

```text
使用 $codex-product-worker；若未自动发现，读取【实际 skill 绝对路径】。
项目：【身份】；taskId：【编号】，revision：【N】，mode：【模式】。
合同：【可访问的 task.json 绝对路径】；SHA-256：【真实哈希】。
协议：【protocol.md 绝对路径或正文】；必要产品资料：【实际路径】。
预期代码基线：【SHA、已确认起点及已有改动说明】。
代码写入本聊天实际分配目录；先核对目录、Git、合同 revision/hash、基线，再修改。
按合同完成实现/原型/独立验证，只改归属内文件；状态、证据和 report-rN.md 写自己的分配目录。
完成后在本聊天返回真实目录、代码提交、报告路径与缺口，规划 agent 主动读取。
关键歧义先在本聊天和状态说明，继续独立工作。跨聊天回发需要直接人类授权。
```

合同明确要求完整用户任务、状态反馈与数据链路，避免只按菜单标题拼接页面。

## 创建后与恢复

就绪返回的 threadId/hostId 用于后续聊天工具。设置中可能先返回 clientThreadId，保存为 PENDING，按返回的就绪机制取得真实身份，必要时核对 list_threads；不能把 clientThreadId 当 threadId。

`get_worktree_creation_status` 只用于确实返回对应 operationId 的 worktree 操作，不能用任意聊天 ID 查询。超时或结果不明记 UNKNOWN，先核对已有聊天与实际执行情况；无法唯一确定时说明缺失信息，不重复 create_thread。

创建成功后依工具要求，在面向用户的交付中输出真实的 `::created-thread{threadId="..."}`；尚在设置中使用返回的 clientThreadId 形式。示例 ID 不能充当结果。

## 跟进与派修复

派单后显式用 wait_threads 跟进。合并相关目标，保存游标，单次等待可用 30–60 秒；超时不代表失败。进度不变时拉长间隔并做独立工作，避免反复报告同一快照。完成或需关注后再读必要细节与实际报告。

自由文本只是线索，核对 revision、目录、Git 与运行证据。实现者自检不能直接变成用户接受。关键问题由你整理给用户；未到的业务决定只阻止依赖工作。

取得实质进展时读取执行者分配目录的状态与报告，提取有用结果后刷新中央展示。worktree 内不可见的报告明确记为未取得；不把中央目录的旧状态当作执行者实时进展，不在每次轮询时重新生成页面。

修复消息带 taskId/revision、复现、实际与预期、AC、候选 SHA 与保留行为。实现偏差复用原聊天；独立验证或上下文失真才新建。模型升级需人类已明确允许该模型或本次指定，不自行提高费用层级。

执行者在自己的聊天报告，你主动读取。你的消息不赋予对方向其他聊天回信的权限；人类已明确授权双向消息时按范围执行。

## 集成、继续与后台边界

检查提交差异后在本地候选验证完整流程。独立 review 派固定 base/head SHA 和 AC，报告必须对应同一候选。保留报告、目录、SHA 与用户接受的关联。

规划者恢复先按派单记录、游标、报告与实际 Git 对齐，再继续。当前活跃回合可持续等待和推进；聊天结束或应用关闭后的唤醒并非 skill 自带能力。只有用户要求持续目标、定时跟进或提醒时，才使用实际支持的 Goals/automation。
