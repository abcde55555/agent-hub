# 从现状到下一项可用改进

## 已有项目

先恢复已有资产，核对当前实现，不根据旧聊天直接重新设计整个平台。

1. 查运行入口、当前改动、主要数据对象、现有文档和最近相关提交。区分代码存在、能启动、行为已验证、用户已接受。
2. 选一个用户正在受困的任务，按实际入口、步骤、输入、输出走一遍。能运行时观察实际页面与存储；环境缺失则记录缺口并查相关实现，代码阅读不等于试用。
3. 形成三栏结论：**有证据的现状 / 用户希望发生的变化 / 尚需验证的解释**。从差距中选下一项。
4. 引用现有文档作为权威来源。冲突时指出具体规则与实现，澄清有业务影响的部分。保留仍在使用的流程与数据兼容性。
5. 没有有效 Git 时如实记录，先做规划与局部验证。建仓库、选择远端或迁移历史需要确定用户意图；空 `.git` 目录不代表能隔离开发。

## 按不确定性选工作

| 当前未知 | 下一项产出 | 离开该阶段的证据 |
|---|---|---|
| 用户到底要完成什么 | 谁、起点、输入、行动、最终产物构成的一条场景 | 用户确认该场景值得解决 |
| 测试、产品、用例等对象关系不清 | 一个场景中的对象关系、归属、状态与操作顺序 | 关键业务含义一致，未知可单独验证 |
| 用户需要用了才知道 | 可操作原型或现有产品中的最小可逆切片 | 用户实际完成任务并指出困惑；模拟边界明确 |
| 目标已清楚 | 带写入边界、AC 和证据要求的实现工作包 | 另一执行者能据此实现和检查 |
| 修改后仍不好用 | 对照修改前后的步骤与结果，定位失效假设 | 下一次改动有一个可检验的解释 |

材料只做到足以支持当前决策。原型可用受控样例；真实保存、重新进入、执行、产出结果等行为只有接入并核验后才作为实现证据。合规产品原型不构成法规解释或真实设备判定。

## 任务与反馈

合同回答：谁从何处进入、对象怎样关联、动作前后状态怎样变、空状态和失败如何反馈、刷新重入后保留什么、最终产物在哪里。只覆盖当前任务涉及的细节。

AC 用“初始状态 + 动作 → 可观察结果”表达。例如：

> 从模板创建产品测试后，用例有可追溯来源；之后修改模板，已创建测试如何变化按已确认规则处理。

这只示范验收写法；模板快照或实时引用的规则仍需业务确认。体验目标可写为待观察假设，例如用户能否说清当前测试对象与下一步，实际试用后再判断。

- **实现偏差**：保留合同，带复现证据派修复。
- **交互方案无效**：保留目标，用小改动验证新交互假设。
- **业务含义改变**：记录用户决定，升级 revision，核对受影响依赖。
- **新增范围**：进入下一工作包；确需一起完成才改当前合同。
- **环境不足**：记 BLOCKED 或 NOT_TESTED，先恢复必要环境。

修订前保留旧版，确认旧执行停止或完成，再发新 revision。记录失败尝试；重复没有新证据的修改返回诊断，不继续堆任务或窗口。

## 增加执行者

完整任务涉及多个菜单仍可由一个人负责。新增执行者需要稳定依赖、可分的文件归属和明确集成责任；共享数据模型、路由或公共组件由一个任务维护。模块负责人只在长期独立模块确有需要时保留。内部子 agent 遵循实际授权，与独立聊天分别管理。

记录修改次数、用户困惑点、实际介入时间、回归与耗时，用结果调整分工。模型或窗口数量本身不能证明质量提升。
