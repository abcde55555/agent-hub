# 实现、原型与 Git 交接

## 实现之前

读必要实现与产品关系，确认当前是补全流程、修复偏差还是验证交互假设。查现有组件、接口、样式与数据定义，复用项目惯例。

对照动作链说明输入、当前对象、状态变化和最终产物。菜单、产品、用例、结果等名词核对实际关系；分别建页面不足以证明流程连贯。

Git 基线核对真实 SHA。要求确切 HEAD 时逐字匹配；允许基线后的已声明提交时检查祖先关系及差异。未声明漂移、已有脏改动或依赖未就绪先记录，保留原状，不用 reset/clean 来“恢复干净”。

## 实现与反馈

完成合同要求的正常路径、空状态、错误反馈与恢复操作。持久化检查刷新重入；异步动作呈现运行状态与结果。复杂度按当前任务确定。

prototype 使用样例或 mock 时，报告可操作部分、演示部分与待用户验证的假设。implement 按合同接入真实行为；接口或环境缺失明确报告，不以模拟成功代替真实成功。

需要改公共接口、共享组件或其他任务归属时，说明必要性、影响和最小调整，由规划者协调。范围内技术修复继续；业务含义与 AC 变更等相应决定。

修复前复现具体问题，记录观察和预期；之后用同场景验证并检查受影响邻接流程。方法反复无效时报告证据并调整诊断。

## 验证

运行仓库要求及变化必要的检查。测试覆盖业务行为与真实缺陷；低影响文案、样式用相应实际检查，不机械写重复实现的测试。

涉及 UI 时实际启动并操作候选，核对反馈、数据和必要截图。工具或环境不可用时标明仅靠代码或自动测试判断的项目。命令、API、浏览器行为与持久化分别举证。

证据关联代码候选 SHA、需求 revision 和环境。账号、网络写入等外部动作遵守当前授权；保持验收标准独立于实现结果。

## 提交与交接

1. 检查差异、状态与归属，显式 stage 自己拥有的路径；保留他人改动。
2. 已授权开发且环境允许时提交连贯改动，遵循项目规则；远端推送、PR 合并和发布另按实际授权执行。
3. 默认分离**产品工作提交**与**报告/运行状态**，方便只集成工作提交。先记产品 SHA 再写报告，文档另提交时分别列出。无法提交时说明原因和精确差异。
4. detached HEAD 可提交并交接真实 SHA；分支依照用户与项目要求操作。无有效 Git 时如实交付文件和验证，不能声称已有提交保证或擅自重建仓库。
5. 状态和报告写自己的分配目录；中央合同来自另一 worktree 时保持内容与 revision，不回写中央调度文件。规划者从你返回的路径读取。

交接列产品提交、报告提交（如有）、归属、真实启动命令、环境和数据、逐 AC 证据、缺口与复现。报告被读取、证据保留前保留工作目录。集成候选由规划者验证，用户明确反馈后才算用户接受。

需要向人解释实现时，复用上述交接，用简短的“用户动作 → 关键文件或接口 → 验证证据”说明，并记录会影响使用或后续维护的取舍。状态和报告留在自己的分配目录，提供实际路径；不额外复制任务状态到 HTML。待真人反馈不阻止不依赖反馈的已明确工作。
